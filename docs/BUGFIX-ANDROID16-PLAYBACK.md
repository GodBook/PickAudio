# Android 16 播放稳定性修复（2026-10-08）

本次修复针对播放中途停止、后台恢复播放失败和媒体服务启动时限问题，发布版本为 1.4.1/code 14。本记录描述修复及其验证范围；初次本地播放回归使用带修复的 1.4.0/code 13 构建，版本提升后的发布验收在下方补充。

## 已确认的问题

`ExoPlayer.isPlaying` 在缓冲和短暂失去音频焦点时也会变成 `false`。此前 `onIsPlayingChanged(false)` 直接把界面状态写成 `PAUSED`，随后播放服务撤下前台状态。用户仍然希望继续播放，但服务与界面已经按照暂停处理。

在同一台专用 API 36 模拟器上，旧 Debug 包的两项回归均失败：

- 可控音频流在播放约三秒后停止供应数据，预期 `BUFFERING`，实际 `PAUSED`。
- 请求短暂音频焦点，播放器仍保留播放意图，实际界面却变成 `PAUSED`。

旧包报告：`app/build/playback-stability/baseline-instrumentation.txt`。

此外，原来的恢复流程先调用 `player.play()`，再异步启动前台服务。Android 15 及以上对后台音频焦点请求要求应用拥有前台服务，这个顺序会导致恢复请求被拒绝。Media3 的无 action 自启动请求也可能在暂停之后才送达，不能假定此前的前台状态仍然存在。

## 修复行为

- 根据播放意图、真实缓冲状态和实际播放状态更新界面。缓冲保留 `BUFFERING`，短暂焦点中断保留播放意图和前台服务；焦点返回后由 ExoPlayer 恢复。播放器及迷你播放器的暂停按钮按播放意图显示。
- 播放和恢复播放等待服务确认已进入前台，再交给 ExoPlayer 申请音频焦点。等待、解析和重试均可被主动暂停或切歌取消；启动失败显示可重试错误。
- 服务处理每个启动请求时先满足前台时限，包括暂停后迟到的 Media3 请求。复用已有媒体通知，不在启动回调中触发 Media3 通知更新，保留暂停通知的媒体控件。
- 前台服务启动被系统拒绝或缺少权限时，停止该次播放并显示错误，处理服务回调中的异常。
- 在线流连接失败、连接超时及指定的临时 HTTP/地址过期错误，会重新解析同一首歌、同一音质，并从中断位置继续。每次播放最多自动恢复两次；主动暂停、清空队列、切歌和服务销毁取消恢复。解码失败、失效文件及文件权限错误直接交给现有错误处理。
- 音源请求超时转换为可重试错误，结束本次加载状态。

## 回归范围

新增 `PlaybackStabilityTest` 六项设备测试：真实缓冲后续播、真实音频焦点抑制与主动暂停、快速取消/重启、暂停后迟到的服务请求、耗尽底层传输重试后的同进度续播、恢复期间主动暂停。可控数据源经过真实 Media3 解码和播放器回调；网络恢复夹具在重连时回到同一音频的本地文件，以隔离外部音源可用性。

另复验原有媒体控制、重复队列快照、后台自然切歌、睡眠取消解析及服务销毁测试。

已通过 71 项 JVM 单测、8 项 API 36 设备回归、Debug/Release 构建、Debug Lint（0 错误、64 警告）和 Room schema 核查。完整播放回归结果记录在 `app/build/playback-stability/fixed-instrumentation.txt`（346.71 秒，无失败或跳过）。

设备实际配置 `fgs_start_foreground_timeout=10000`。快速取消/重启与暂停后迟到服务请求两项专项均等待 11 秒，超过系统时限；额外定向复验 2 项通过（48.261 秒），报告为 `fixed-deadline-instrumentation.txt`。暂停状态、有效媒体通知及再次播放均符合预期。

设备为本次新建、无个人数据的 `PickAudio_Playback_API36_20261008` / `emulator-5560`。首次运行测试框架时出现类校验启动超时，系统应用也出现同类超时；完成应用和测试包的 `speed` 预编译后再进行上述旧包对比。该环境启动异常记录在 `baseline-startup-anr.txt`，不作为播放修复的复现依据。

这些结果覆盖 API 36 模拟器；用户手机的原始崩溃日志、实体蓝牙和厂商后台管理策略尚未验证。
