用户指定当前 USB 手机，序列号 `1944b301`，Android 15/API 35，arm64，60 Hz，LineageOS。开始时未安装拾音。本轮对该手机安装和操作测试实例，测试音乐为生成的静音 WAV；未删除或改写手机个人音乐。

修正后的 28 项定向回归全部通过，覆盖后台焦点、20 秒无进展恢复、随机自然切歌、媒体通知、批量操作、新增逻辑和真实界面操作。最终 Debug 与 validation 整组各 102/102 通过，无失败或跳过（分别 488.416、440.577 秒）。CI 中曾超时的服务停止/重试专项，在同一手机 validation 独立连续三次通过（13.242、13.101、13.103 秒）。

手机验证用公开调试证书副本与正式包的生产 DEX 完全相同，未保留 validation 的公共测试 ABI。冷恢复显示暂停在 0:02、含 3 个重复条目的列表循环队列；通过实际界面播放后，14 次后台观测覆盖至少 70 秒，观察到自然切歌。12 次媒体通知下一首逐次确认当前队列条目变化，前台服务和进程保持，暂停后返回界面恢复播放通过。证据：`phone-production-smoke.json`、`phone-production-background-samples.json` 与 UI XML。未对实际生产裁剪副本运行白盒 instrumentation。

随后核对已安装测试副本的 APK 摘要，卸载本轮创建的测试实例和测试包，安装原签名正式 APK；从手机提取的 APK SHA-256 与发布候选完全一致。实际通过系统文件选择器导入本轮生成的 20 秒 WAV（新增 1、失败 0）、本地播放、设置与关于页面。真实在线搜索返回 `Love Story`，网易云源返回约 35 秒 MP3 片段，播放器检测为 44.1 kHz/128 kbps，连续会话观测 PLAYING 且进度从 23,932→29,938 ms；这仅证明当时真实网络链路与解码工作，不代表完整歌曲授权/长期音源可用性。

上述测试结束后，清除这个全新安装实例的测试数据，删除唯一生成的外部 WAV，保留原签名 1.5.0。未删除个人音乐；该手机不作为旧正式版覆盖升级设备（旧包不支持 API 35）。

## 同设备性能比较

基线为 v1.4.5 仅放宽 minSdk 至 35 的 Debug 构建，新版为 v1.5.0 Debug。由于旧正式版最低为 API 36，这不是两个正式 APK 在 Android 15 上的直接比较。两组使用同一手机和固定夹具，记录原始样本与测量方法，不把 Debug 数值等同于正式包性能。

| 指标 | 基线 | 新版 | 结论 |
|---|---|---|---|
| 1,000→2,000 条队列，20 次同步主线程 API p50 | 558.48 ms | 5.89 ms | 批量插入明显减少工作量 |
| 同操作 p95 | 583.96 ms | 20.55 ms | 此操作 p95 减少约 96.5% |
| 同操作最大样本 | 590.25 ms | 31.81 ms | 不包含异步落库时间，每轮另行等待持久化完成 |
| 10,000 首夹具，10 次冷启动显示时间 p50 | 2,167 ms | 2,150 ms | 中位数接近，不宣称启动提速 |
| 同场景冷启动 p95 | 2,235 ms | 2,731 ms | 新版出现长尾样本，不能认定启动改善 |
| 20 次热进入 p50/p95 | 87/96 ms | 82/99 ms | 接近，存在系统与测量波动 |
| 20 次 ADB 滚动，系统统计 p95 | 30 ms | 34 ms | 未证实滚动帧改善 |
| 对应慢帧比例 | 5.82%（962 帧） | 8.95%（581 帧） | 帧数与调度不完全相同，不作为严格配对帧率结论 |
| 上述启动采样后的单次进程 PSS | 149,812 KiB | 149,450 KiB | 接近；不是长时间内存或泄漏验收 |

队列计时调用实际 `PlaybackCoordinator.addTracksToQueue()`，包含列表、随机池、状态发布和快照请求；通过 `flushPersistence()` 核对持久化。设备用例还检查了 2,000 个独立条目身份和重复歌曲。

启动使用 [measure-startup.ps1](../scripts/measure-startup.ps1) 的 `am start -W TotalTime`，表示 Activity 显示时间，不表示曲库全部可用或首个音频输出。滚动使用 [measure-scroll.ps1](../scripts/measure-scroll.ps1) 和系统 gfxinfo；手势驱动的 Compose 测试另有 FrameMetrics 样本，其测试时钟和同步机制会影响帧耗时，不用于声称设备稳定达到某帧率。充电、温度、JIT、系统缓存和其他系统工作均会影响结果。

原始证据保存在 `app/build/release-1.5.0/`：`baseline-paired-performance.log`、`final-paired-performance.log`、`baseline-startup.json`、`final-startup.json`、`baseline-scroll.txt`、`final-scroll.txt`。

另在同一手机上测量本版实际生产 DEX（公开调试证书副本、10,000 首夹具与暂停队列）：10 次进程冷启动显示时间 p50/p95 为 479/499 ms，20 次热进入为 54/65 ms。20 次实际列表滑动采集 683 帧，p95 为 13 ms，系统慢帧 1/683（0.15%）。这是当前裁剪代码的单版本数据，不能与上表 Debug 直接作改进百分比比较。证据：`production-startup.json`、`production-scroll-final.txt`。

生产滚动首次采样未产生帧：按屏幕固定比例发出的手势落在迷你播放器区域。测量脚本已改用真实可滚动区域的 bounds，并拒绝零帧样本；修正后重新采集。后续仍需同配置正式包配对、长时间内存、并行下载、实体蓝牙、TalkBack 及脱离 USB 的耗电专项；本版未引入 Macrobenchmark/Baseline Profile，不将现有观测称为所有性能目标均已达成。

## 失败记录与修正

首次新增专项中两项因构建期间继续改动导致主/测试 APK 接口版本不一致，固定源码并成对重建后修正。首次完整手机回归 102 项中 4 项失败，分别修正 API 35 安装测试夹具、媒体资源变更后重新启动远程停滞监测、综合选择范围的旧断言，以及重复移除帧监听器的测试清理。

首轮 CI 四组均在新增多选用例中点击了窄屏外的操作按钮。补充滚动、可见/可用检查及限时结果确认，保留 20 首和平台归属断言后重跑。原失败日志与 CI 报告保留，不将这些轮次计为通过。首轮自动启动测量未取得 TotalTime，保存失败并重新执行完整采样。

手机生产代码脚本首轮错误地读取 PowerShell 数组的 `Item` 索引器，导致“未观察到切歌”的误判。改为逐样本读取条目字段并保存全部观测值后完整重跑通过；实际应用和 DEX 未修改。
