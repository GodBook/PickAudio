# 拾音 PickAudio 操作体验与性能优化更新计划

审查日期：2026-10-15（Asia/Shanghai）

审查版本：v1.4.5 / versionCode 18，Room v5

源码基线：`217546baeefc97b49aa21eb0ba2e373052c880e5`

文档状态：下一轮更新建议，全部条目待实施；本文不代表功能已经更新或版本已经发布。

## 1. 审查结论与范围

当前软件的主要流程已齐全，下一轮最值得投入的是操作结果可预期、大批量操作不阻塞界面，以及减少播放期间的重复工作。建议先修正搜索多选范围、从音源管理返回时的自动重播、下载文件检查占用主线程和批量队列的累积开销，再处理查询、写盘、通知和渲染频率。

本次检查了导航、曲库、搜索、歌单、播放器、歌词、下载、设置，以及对应的 Room、DataStore、音源解析、缓存与测试代码。结论分为三种证据：

| 标记 | 含义 | 使用方式 |
|---|---|---|
| A | 可以从当前源码确认的行为、调用链或算法开销 | 可以据此安排修正；不等于已测出设备卡顿程度 |
| B | 需要设备或受控网络测量的影响 | 实施前后补充耗时、帧、内存、I/O 或耗电对比 |
| C | 可选的体验或功能扩展 | 单独安排，不作为已有缺陷描述 |

本轮以源码审查为主，没有进行实体机操作体验、帧率、CPU、PSS、耗电或外部音源延迟测量。因此，下文的性能收益是优化方向，验收数值是建议目标，不是当前软件的实测结果。历史测试结果仅引用原记录，不作为本轮设备验收。

### 1.1 已有成果应保留

根据当前代码及 [v1.4.5 验证记录](VALIDATION-1.4.5.md)，以下能力已有实现，不应重复作为“新增修复”立项：

- 搜索分平台分页、独立重试、取消与代次隔离；试听返回保留当前进程内的搜索结果和滚动位置。
- 曲库明确入库，试听、喜欢、歌单和下载不会自动入库；导入可取消，已导入结果保留。
- 歌单查询限定成员范围，曲库索引与筛选在后台执行，界面订阅遵循生命周期。
- 队列条目拥有独立身份，重复歌曲可区分；v1.4.5 已修复随机时间线环路，并固定时长与顺序快照。
- 后台播放前台服务、音频焦点、限次原进度恢复、下载执行代次和公共文件发布恢复。
- 本地音频绕过网络缓存、音质事实校验、缓存分类清理、备份校验与迁移、Release 的 R8 和资源裁剪。

旧审查及执行记录见 [2026-10-06 审查](OPTIMIZATION-REVIEW-2026-10-06.md) 与 [优化执行记录](OPTIMIZATION-EXECUTION.md)。本轮使用 N01–N16 编号，避免与已完成的 O01–O24 混淆。

## 2. 日常操作逻辑

| 操作路径 | 当前行为 | 下一轮建议 |
|---|---|---|
| 搜索 → 多选 → 加歌单/下载/队列 | 渲染按平台筛选，但“全选”和执行对象使用所有已加载平台结果 | 统一显示范围、选中数量和实际操作对象；跨平台选择必须明确提示 |
| 播放器 → 音乐源管理 → 返回 | 只要从播放器进入，就在离开音源页时重试并展开播放器 | 未修改时恢复原状态；修改后保留歌曲、进度、音质和原播放意图 |
| 下载 → 已完成 | 检查全部已完成文件，文件访问检查可能在主线程执行 | 先展示列表，后台核验；仅刷新失效行，支持取消核验 |
| 多选歌曲 → 加入队列 | 逐首插入；每次插入复制队列并重建随机池 | 一次批量更新，保留条目身份与随机播放语义 |
| 多选歌曲 → 选择下载音质 | 按每首歌重复读取平台音源能力 | 按不同平台读取一次，再计算共同可用音质 |
| 重复扫描/导入同一目录 | 重新读取和更新大量已知文件；短音频跳过未计入进度 | 识别未变化文件，清楚报告新增、更新、跳过与失败 |
| 修改歌词字号 | 滑动过程直接提交偏好写入 | 本地即时预览，结束拖动后保存最终值 |
| 首次打开曲库/歌单 | 数据未到达时用空集合表示 | 区分加载中、确实为空、筛选无结果和读取失败 |

## 4. 具体更新项

### N01：搜索多选与当前结果范围一致

现状依据：[SearchScreen.kt](../app/src/main/java/com/pickaudio/ui/screens/SearchScreen.kt) 第 61–62、108、137–144 行，以及 [SearchStateManager.kt](../app/src/main/java/com/pickaudio/ui/screens/SearchStateManager.kt) 的 `searchResults`。`allTracks` 汇总全部平台已加载结果，“全选”和批量执行都使用该集合；界面却按当前平台渲染，综合页每个平台只显示前五首。

具体例子：两个平台各加载 20 首后，切到 QQ 页点击全选，会选中 40 首；综合页只展示 10 首时，也可能选中 40 首。这是可由源码确认的范围不一致。

建议：建立同一个结果范围模型供渲染、全选、计数和执行使用。默认全选“当前平台已加载结果”；综合页默认选择当前展示结果。切换平台时清空选择；如果以后支持跨平台保留选择，应显示各平台数量及明确入口。使用“已加载”描述分页范围，不暗示包含尚未请求的歌曲。

验收：双平台各 20 首时，QQ 全选为 20 首，综合摘要全选为 10 首；加入歌单、下载和队列的对象与确认数量一致。覆盖加载下一页、切换平台、清空搜索和返回播放器后的选择状态。

### N02：从音源管理返回时保留播放上下文

现状依据：[MainActivity.kt](../app/src/main/java/com/pickaudio/MainActivity.kt) 第 89–99、298–301 行；[PlaybackCoordinator.kt](../app/src/main/java/com/pickaudio/playback/PlaybackCoordinator.kt) 的 `retryCurrent()` 和 `playTrack()`。进入音源页设置 `retryAfterSource = true`，离开时无条件重试并展开播放器。重试保留进度和请求音质，但没有传入原播放意图，`playTrack()` 默认自动播放。

影响：暂停状态进入音乐源管理，即使不修改配置，返回也可能开始播放；仅查看设置会重新解析、打断已有播放。当前音质不被新音源支持时，又可能直接得到失败。

建议：记录进入时的歌曲/队列条目、播放意图、进度、请求音质和相关平台源配置；返回时比较配置版本。未变化则只恢复界面，已变化才重解析，并显式传入原播放意图。若当前音质不受支持，先展示可用音质供选择。原播放条目已变化时，不恢复过期上下文。

验收：暂停→查看音源→返回仍暂停；播放→未修改→返回不中断；换源后保留进度和暂停/播放意图；不支持原音质时有可操作提示。继续保留 QQ 候选录音须人工确认的行为。

### N03：已完成下载文件核验移出主线程

现状依据：[DownloadScreen.kt](../app/src/main/java/com/pickaudio/ui/screens/DownloadScreen.kt) 第 39 行由 `LaunchedEffect(tab)` 调用 `refreshCompletedFiles()`；[DownloadCoordinator.kt](../app/src/main/java/com/pickaudio/download/DownloadCoordinator.kt) 第 283–288 行逐项执行 `checkAssetAccess()`；[AssetAccess.kt](../app/src/main/java/com/pickaudio/data/repository/AssetAccess.kt) 同步执行文件检查或 `openAssetFileDescriptor()`。

Room 的挂起查询不会自动把后续代码留在 I/O 线程。查询返回调用方后，文件访问仍可能发生在 Compose 主线程。下载历史较多、存储提供者响应较慢时，存在明显的界面阻塞风险；具体时长待测。

建议：在仓库/协调器边界用 `withContext(Dispatchers.IO)` 包住核验，增加逐项取消检查，先展示已有列表，再后台更新。针对当前页和最近变化文件优先核验，避免每次切换都完整打开全部文件。UI 的“打开文件”仍需处理权限或文件在核验后发生变化的情况。

验收：1,000 条完成记录及慢响应文件提供者下，切换标签、滚动和返回可持续响应；StrictMode/线程记录确认文件访问不在主线程；离开页面能取消剩余检查，失效文件准确转入需处理状态。

### N04：队列更新采用批量操作，并限制待写快照

现状依据：[SearchScreen.kt](../app/src/main/java/com/pickaudio/ui/screens/SearchScreen.kt) 第 112 行和 [DownloadScreen.kt](../app/src/main/java/com/pickaudio/ui/screens/DownloadScreen.kt) 第 72 行逐首 `addToQueue()`；[PlaybackCoordinator.kt](../app/src/main/java/com/pickaudio/playback/PlaybackCoordinator.kt) 第 392–396 行的批量接口内部仍逐首插入；[PlaybackQueue.kt](../app/src/main/java/com/pickaudio/playback/PlaybackQueue.kt) 的 `insert()` 每次复制列表并 `resetShuffle()`。

将 m 首加入已有 n 首的队列，其列表与随机池处理量随 `n×m + m²` 增长，发生在界面调用路径。每首单独加入还会重复发布状态和创建快照。当前快照 writer 已会合并待写请求，但 `Channel.UNLIMITED` 仍可在慢数据库期间积累完整快照。队列拖动也会在每次交换位置时请求持久化。

建议：增加队列模型的真正批量插入，一次生成条目身份、拼接列表、更新随机池并发布。拖动期间使用预览状态，结束后提交，避免连续写盘。将普通保存请求改为有界的最新状态槽，显式 `flushPersistence()` 保留完成确认，不能简单丢弃有 completion 的请求。复用同一不可变时间线/媒体元数据快照，按队列、模式、当前条目及已知时长变化失效；保留 v1.4.5 的有限遍历约束。

验收：分别测量 100、1,000、10,000 条队列，及已有 1,000 条再加入 1,000 条的主线程耗时、分配量和待写请求峰值；一次批量操作只发布一次最终队列。重复歌曲身份、随机池覆盖、上一首历史、拖动后当前条目和冷恢复保持正确；时间线比较/哈希/序列化回归继续通过。

### N05：按平台复用音源能力和初始化结果

现状依据：[MusicActions.kt](../app/src/main/java/com/pickaudio/ui/components/MusicActions.kt) 的 `DownloadQualityDialog` 对 `online` 每首歌调用 `supportedQualities()`；[LxSourceManager.kt](../app/src/main/java/com/pickaudio/source/LxSourceManager.kt) 第 126–131、387–441、454–460 行。能力查询会执行内置源检查；一次解析先检查内置源，再经能力查询检查一次。内置源检查有互斥锁，但仍重复计算脚本摘要、查询记录和插入默认绑定。

建议：下载弹窗先取不同平台，至多查询网易云和 QQ 两组能力。内置源初始化采用单次共享进行中的任务和版本化结果；失败可重试，脚本/应用版本改变时重新验证。平台选择与启用状态仍读取最新数据，不能把用户切换、明确停用或恢复后的配置缓存成旧值。批量入队一次取得能力快照，执行前按配置代次确认有效。

验收：同平台 1,000 首打开音质弹窗，能力读取不随歌曲数线性增加；同版本已初始化后不重复写默认绑定或计算内置脚本摘要。首次安装、并发首次请求、自定义源、明确停用和备份恢复回归通过。

### N06：减少无变化写入和整库重建

现状依据：[PlaybackCoordinator.kt](../app/src/main/java/com/pickaudio/playback/PlaybackCoordinator.kt) 第 222、770 行会写入音频信息；[Daos.kt](../app/src/main/java/com/pickaudio/data/db/Daos.kt) 第 51–52 行的 UPDATE 没有“值变化”条件。[LibraryRepository.kt](../app/src/main/java/com/pickaudio/data/repository/LibraryRepository.kt) 第 233–241 行组合全部资源、在线引用、收藏及曲库歌曲；[LibraryBrowserViewModel.kt](../app/src/main/java/com/pickaudio/ui/screens/LibraryBrowserViewModel.kt) 对每次歌曲集合发射重新构造索引。

影响：一首本地歌曲开始播放或重新 READY，即使音频信息没有变化，也可能使资源表失效、重新查询，并触发整库投影与索引构建。当前筛选已经在后台执行，剩余问题是计算频率和范围。

建议：在 DAO 层使用空值安全的差异条件，仅实际变化时写入音频信息、可用性及元数据；为查询结果添加合适的去重。曲库关联只读取曲库相关资源和引用，避免纯试听记录增长影响曲库加载。将文本索引与收藏、文件可用性等状态更新分开，先验证增量更新收益，再决定是否需要 Paging/FTS。

验收：10,000 首曲库反复播放同一首本地歌曲，音频事实不变时不再更新资源表、不重建文本索引；修改收藏仍即时显示。记录查询次数、索引构建次数与 CPU，而非只记录一次筛选耗时。

### N07：偏好去重，滑块先预览再保存

现状依据：[UserPreferences.kt](../app/src/main/java/com/pickaudio/data/preferences/UserPreferences.kt) 中偏好字段由 `dataStore.data.map` 派生，没有字段级 `distinctUntilChanged()`；[PickAudioApplication.kt](../app/src/main/java/com/pickaudio/PickAudioApplication.kt) 直接 collect 缓存容量并调用配置；[LibraryBrowserViewModel.kt](../app/src/main/java/com/pickaudio/ui/screens/LibraryBrowserViewModel.kt) 将最近播放列表参与组合。设置页第 192 行、播放器第 253 行的歌词字号 Slider 在每次值变化时直接提交 DataStore 写入。

影响：更新搜索历史或歌词字号也会让不变的缓存容量、最近播放字段重新发射，触发容量配置或曲库筛选等下游工作。即使 Compose 对相同值避免重组，业务 collect/combine 的重复执行仍可能发生。

建议：偏好字段或统一设置状态在映射后去重；缓存容量仅在配置实际改变时应用，低空间检测使用独立触发条件。滑块用本地状态即时预览，拖动结束保存一次，必要时增加节流和离开页面时的最终提交。只在当前所需子页订阅详细数据，避免无关设置牵动业务逻辑。

验收：连续拖动字号，预览跟手且最终值保存正确；搜索历史更新不触发缓存重新配置，非最近播放字段变化不触发曲库重新筛选。验证恢复偏好、系统主题和六种配色仍即时生效。

### N08：下载进度与数据库、通知分开刷新

现状依据：[DownloadCoordinator.kt](../app/src/main/java/com/pickaudio/download/DownloadCoordinator.kt) 第 479–485 行每 500 ms 经 `mutate()` 读记录并写完整任务；第 67–69 行暴露冷的任务全表 Flow。[DownloadScreen.kt](../app/src/main/java/com/pickaudio/ui/screens/DownloadScreen.kt) 第 45–49 行每次对全表分组；[DownloadJobService.kt](../app/src/main/java/com/pickaudio/download/DownloadJobService.kt) 每次任务列表发射都调用通知更新，即使通知显示的活动标题与数量没有改变。

两首并发时，传输循环理论上可产生约四次进度读写/秒，实际受网络与锁影响。UI 和通知分别订阅冷 Flow，也会分别触发查询。`distinctUntilChanged()` 只能去掉内容相同的结果；字节数持续变化时不能消除这些刷新。

建议：实时进度保留在内存状态，数据库以较低频率保存恢复检查点；暂停、失败、完成及发布阶段仍立即持久化并遵循执行代次。UI 仅订阅当前页和活动任务，历史完成记录按需加载。通知提取实际展示字段，字段去重后再更新。下载进入前台所需的初次通知不得延迟；检查点频率必须与崩溃后的实际 `.part` 长度核对配套。

验收：两首下载与 1,000 条历史记录并存时，分别记录 SQL、写盘、通知调用及主线程分组次数；字节变化但标题/数量不变时不重复更新相同通知。维持进度可见性，并通过暂停/继续、进程中断、网络切换和发布中断回归。

### N09：缩短首播与切歌准备路径

现状依据：[PlaybackCoordinator.kt](../app/src/main/java/com/pickaudio/playback/PlaybackCoordinator.kt) 第 647–719 行在当前歌曲结束后才处理下一首，并依次完成前台服务确认、歌曲身份持久化、地址解析、缓存身份探测与播放器准备。[AudioCacheResolver.kt](../app/src/main/java/com/pickaudio/playback/AudioCacheResolver.kt) 在起播前串行执行最多 1,500 ms 的 HEAD 探测。[LxSourceManager.kt](../app/src/main/java/com/pickaudio/source/LxSourceManager.kt) 第 100–115 行无参数 `audioClient()` 每次创建新的基础 OkHttpClient；播放器数据源和缓存 HEAD 使用不同调用取得客户端。

建议先做低风险优化：复用有明确用途的 HTTP 基础客户端与连接池，按网络路由派生客户端；观察 DNS、连接和 TLS 时间。为相同资源身份建立短期的验证器结果缓存；HEAD 不支持或已验证过的资源避免重复探测。保留强 ETag、If-Match、重定向和完整 URL 降级策略，不能为节省探测而跨不同资源复用缓存。

后续可在当前歌曲稳定播放后，低并发预解析确定的下一条队列项，并绑定队列条目、模式、音质和源配置代次；切换、暂停、删除或配置变化时取消，地址过期重新解析。移动网络默认不预下载音频；地址解析也有网络开销，应纳入流量预算。预解析地址只能减少等待，真正无缝播放还需要播放器连续准备/缓冲方案，作为独立功能验证。

验收：分别记录本地、QQ 直连、脚本源的冷/热首播，以及自然切歌间隙；控制网络后比较各阶段耗时。弱网、HEAD 超时、过期地址、源切换、快速下一首、后台音频焦点和候选录音确认均保持正确。不要通过移除前台服务确认来缩短时间。

### N10：播放进度局部刷新，歌词按需加载

现状依据：[PlayerScreen.kt](../app/src/main/java/com/pickaudio/ui/screens/PlayerScreen.kt) 第 51 行在整个页面读取播放进度，第 103–109 行在页面打开和切歌时加载歌词，与封面/歌词标签无关；队列弹层显示时，第 239–240 行还会随页面执行映射条目 ID。[PlaybackDiagnostics.kt](../app/src/main/java/com/pickaudio/playback/PlaybackDiagnostics.kt) 每次音频读取都复制并发布统计状态；[SettingsScreen.kt](../app/src/main/java/com/pickaudio/ui/screens/SettingsScreen.kt) 在根部建立该订阅。

建议：将进度条、时间文字和歌词高亮拆成读取高频状态的局部组件，封面、歌曲信息、菜单和队列使用稳定状态。歌词首次进入标签时加载，保留已有缓存和切歌隔离；需要预取时安排在起播后。字节计数先用轻量累计，再按固定低频发布统计快照，“关于”页显示时再订阅。歌词行定位已使用二分查找，应保留。

验收：用 Compose 重组记录确认封面/菜单不因每 500 ms 的进度变化重复处理，队列 ID 不随进度重复构建；只查看封面不会发起歌词网络请求。拖动进度、快速切歌、手动歌词校准、翻译、大字号和返回当前歌词均通过。

### N11：重复导入增量处理，封面维护按批次执行

现状依据：[LibraryRepository.kt](../app/src/main/java/com/pickaudio/data/repository/LibraryRepository.kt) 第 254–305、319–353 行。MediaStore 扫描逐首写入；SAF 导入在判断已有资源之前调用 `AndroidAudioProbe.inspect(..., artwork = true)`。第 185–201 行的 `saveArtwork()` 每处理一张封面就列举目录、计算大小并排序清理。`startImport()` 与扫描/目录方法还会重复准备资源索引。

影响：第二次导入相同目录仍要读取音频头、元数据和内嵌图片，并重复写记录；封面数量增加后，目录维护成本叠加。当前已经做到每个 SAF 目录一次列举子文件，应保留这一实现。

建议：通过规范化 URI、大小、修改时间及提供者可用的 generation 判断变化，未变化文件复用音频事实和封面。未知/不可信的变更信息不能仅凭同名或同大小断言相同。对新文件采用小批事务与节流进度更新，取消后保留已提交批次。封面目录统计在批次末尾或触发容量阈值时执行；资源索引每个导入任务准备一次。

验收：固定 1,000/10,000 首目录，比较首次和第二次导入的文件打开次数、元数据读取、DB 写入、封面目录列举和耗时；修改一首文件仍更新对应记录。稳定歌曲 ID、同名不同录音、同目录 LRC、手动歌词优先级与取消保留结果不能回退。

### N12：扫描统计和进度口径一致

现状依据：[LibraryRepository.kt](../app/src/main/java/com/pickaudio/data/repository/LibraryRepository.kt) 第 269、277、303–305 行。进度总数来自查询游标计数，过滤短音频时直接 `continue`，没有增加 `processed` 或 `skipped`。因此开启短音频过滤后，处理数可能达不到总数，完成报告也少算跳过项。

建议：总数、已检查、成功处理使用明确口径。短音频计入“已检查”和“因时长跳过”；把重复未变化、更新、时长过滤和失败分开统计。多卷扫描时说明仍在发现文件，避免总数扩大时让进度产生误解。

验收：输入 10 首，其中 3 首因时长过滤，完成时已检查 10、跳过 3，其余各类合计一致。覆盖重复导入、多个存储卷、无权限、部分失败和取消，不将未检查项算作成功。

### N13：页面加载、恢复和错误状态补齐

现状依据：[LibraryBrowserViewModel.kt](../app/src/main/java/com/pickaudio/ui/screens/LibraryBrowserViewModel.kt) 的 `LibraryViewState()` 只有空集合和错误，没有初始加载状态；`catch` 发出错误后该次上游收集结束，没有显式重试触发。[PlaylistDetailScreen.kt](../app/src/main/java/com/pickaudio/ui/screens/PlaylistDetailScreen.kt) 查询与选择使用 `remember`；[SearchStateManager.kt](../app/src/main/java/com/pickaudio/ui/screens/SearchStateManager.kt) 为应用内存对象，不具备进程死亡后的查询恢复。

建议：页面使用 Loading/Content/Empty/Error 状态，保留旧内容并显示刷新状态；错误提供真实重新订阅的入口。查询、平台、筛选和锚点使用 ViewModel/SavedStateHandle 或相应可保存状态恢复；搜索结果大集合不写入 saved instance state，进程重建后按保存查询重新加载。列表锚点优先用稳定条目身份，跨平台切换保存各自位置。删除等敏感待提交操作不自动恢复执行。

验收：慢数据库不会先闪现“曲库为空”；查询失败后可以不重启页面恢复；系统回收进程后查询条件能恢复且无超大 Bundle。播放器覆盖、底部标签切换、旋转/重建及分层返回与现有测试一致。

### N14：批量下载控制报告实际结果

现状依据：[DownloadScreen.kt](../app/src/main/java/com/pickaudio/ui/screens/DownloadScreen.kt) 第 69–72 行，在 `resumeAll()` 发起后立即提示“已加入等待队列”；[DownloadCoordinator.kt](../app/src/main/java/com/pickaudio/download/DownloadCoordinator.kt) 第 359–361 行批量控制为内部 launch 的逐首调用，UI 不获得完成/失败报告；每首恢复还可能分别触发系统调度。

建议：批量暂停、继续、重试、取消返回逐项报告和操作中状态，UI 完成后再显示真实数量；对成功项合并一次调度。执行时确认对象仍有效，已完成、已删除、无法恢复等情况计为跳过或失败；阻止同一批命令重复提交，出错不放弃后续独立项。保留已有 `enqueueBatch()` 的失败项重试报告能力。

验收：100 项中故意设置失败与状态变化，汇总成功、跳过、失败数量准确；系统不接受任务时不显示已成功入队。连续点击、页面离开和执行代次失效都不产生重复操作或旧任务回写。

### N15：低功耗与脚本执行单独测量

现状依据：[PlaybackCoordinator.kt](../app/src/main/java/com/pickaudio/playback/PlaybackCoordinator.kt) 第 251–272、296–325 行。播放中进度 ticker 每 500 ms 执行；停滞监测也以 500 ms 运行，虽然 `active` 会排除本地文件，循环本身仍会启动。[QuickJsEngine.kt](../app/src/main/java/com/pickaudio/source/QuickJsEngine.kt) 的 `evaluateAsync()` 以 20 ms 间隔调用 JNI 查询 Promise 并解析 JSON。[PlaybackCoordinator.kt](../app/src/main/java/com/pickaudio/playback/PlaybackCoordinator.kt) 第 98–119 行对所有歌曲使用相同缓冲、回看与 wake 模式。

建议：本地播放不启动网络停滞监测，后台不可见时减少仅用于 UI 的进度发布，持久化和睡眠定时保留独立语义。评估通过桥接完成通知替代 Promise 轮询，保持每次操作独立引擎、取消、超时和关闭边界。缓冲和 wake 设置先按编码、网络与屏幕状态做对比，再决定是否调整；不要统一缩小缓冲，也不要为了复用而让脚本运行时无限驻留。

验收：在固定实体设备上对比本地/在线、亮屏/息屏的 CPU、唤醒和耗电；脚本长请求记录 JNI 次数、内存峰值和取消响应。耳机断开、蓝牙、焦点中断、断网续播与睡眠定时不受影响。

### N16：建立可靠的性能基准与诊断口径

现状依据：[OptimizationPerformanceTest.kt](../app/src/androidTest/java/com/pickaudio/OptimizationPerformanceTest.kt) 已验证大曲库查询范围并记录筛选耗时，但不覆盖真实滚动帧、启动、耗电和大队列。当前未配置 Macrobenchmark/Baseline Profile 专项。[PlaybackDiagnostics.kt](../app/src/main/java/com/pickaudio/playback/PlaybackDiagnostics.kt) 的 `firstAudioMs` 在 `onIsPlayingChanged(true)` 时结束计时，属于开始播放状态的代理指标；`buffers` 也没有区分首次准备、拖动和真正的再缓冲。

建议：先统一指标定义，再比较优化。分段记录服务准备、数据库、源初始化、地址解析、缓存验证、播放器准备及音频输出事件；区分冷/热、本地/在线、成功/失败。缓冲同时记录原因和持续时间。保留本地导出与聚合统计，记录设备、构建、队列/曲库规模、网络条件和缓存状态。启动/滚动增加正式裁剪代码的 Macrobenchmark，之后再根据结果决定是否引入 Baseline Profile。

验收：同一场景重复执行得到可比的 p50/p95，失败和取消不能混进成功延迟；统计不会引入逐音频块的 UI 刷新。应用自身指标与系统 trace 可对应，不能把开始播放状态直接宣称为耳朵听到首帧的精确时刻。

## 6. 性能验收方案

以下为建议的实施验收方法，尚未执行，也不表示已经达到数值目标。

### 6.1 固定测试条件

- 使用不含个人数据的专用 API 36 设备/模拟器做功能回归；持续帧率、蓝牙与耗电在对应实体机确认。安装、清库和夹具只能针对明确指定的隔离设备。
- 记录硬件、系统、刷新率、构建 SHA、ABI、编译模式、温度/电源状态。比较相同裁剪配置的应用包，Debug 与 Release 不混作同一性能基线。
- 曲库固定为 1,000/10,000 首；队列为 100/1,000/10,000 条，包含重复歌曲；下载历史至少 1,000 条，活动下载固定两首。
- 本地音频固定 MP3/FLAC 样本及封面；在线链路用受控服务分别模拟正常、慢响应、重定向、超时和断流。真实外部音源结果另列，不用不可控平台波动证明客户端提速。
- 冷启动至少 10 次，热进入/操作至少 20 次，记录 p50/p95、失败和异常值；分别记录空缓存与热缓存条件。

### 6.2 验收指标

| 场景 | 要记录的指标 | 建议目标或判定 |
|---|---|---|
| 冷启动、通知冷恢复 | 首次可见、可操作时间，主线程阶段，恢复队列耗时 | 先建立基线；优化后同条件无退步，不把系统启动时间全部归因于应用 |
| 10,000 首查询/分类 | 输入到结果 p95、SQL 数、索引重建次数 | 输入到可见结果 p95 争取 ≤300 ms，包含 150 ms 防抖；报告实际设备条件 |
| 1,000 首批量加队列 | 点击反馈、主线程最长工作、总完成时间、分配量 | 100 ms 内给出可见反馈；结果构建移出长主线程任务，批量状态发布一次 |
| 滚动并行下载 | 帧耗时、FrameOverrun、慢帧比例、重组范围 | 60 Hz 以约 16.7 ms 帧预算观察，120 Hz 以约 8.3 ms；不把 60 Hz 目标套用全部设备 |
| 下载列表及通知 | 每秒查询/写盘/通知次数、历史页分组耗时 | 展示字段不变时不重发相同通知；检查点与实时进度分离，状态转移立即保存 |
| 本地/在线首播 | 分阶段 p50/p95、请求数、TLS/HEAD 时间 | 同受控网络比较；保留资源与音质校验，实际增益以结果为准 |
| 自然切歌 | 当前音频尾部到下一音频输出的间隙 | 单独比较本地和在线；只完成地址预解析时不宣称无缝 |
| 重复导入 | 检查/更新/跳过数、文件读取及写盘次数 | 未变化文件不重复深读和写入，修改文件准确更新，取消结果可恢复 |
| 连续使用 60 分钟 | PSS/Java/native 堆、GC、队列待写峰值 | 观察稳态及回收后趋势，解释缓存增长；无无界积压，不能只凭单次峰值判断泄漏 |
| 息屏播放 | CPU、唤醒、服务状态、单位时间耗电 | 同设备同音量/网络/时长配对比较，后台连续播放和定时停止优先保证 |

### 6.3 必须保留的回归场景

搜索代次与分页隔离；QQ 原曲校验和候选确认；真实音质与下载完整性；重复队列条目；随机时间线有限遍历；后台无控制器自然切歌；通知暂停/恢复；音频焦点与耳机断开；断流原进度续播；快速暂停/继续/取消；下载发布中断；手动歌词与校准；曲库归属；备份、迁移和原签名覆盖升级。TalkBack、实体蓝牙及 OEM 行为按实际设备验证范围记录。
